# Безопасность и персональные данные

Что защищено, как показываем сервис экспертам и что сделать перед сдачей.

## Что уже сделано

- Пароли храним только как хеш argon2. В открытом виде их нет ни в базе, ни в ответах сервера.
- Сессия в cookie с httpOnly и SameSite=lax: скрипты на странице ее не читают, чужие сайты ее не отправляют. На сервере с https включаем `COOKIE_SECURE=true`.
- Ключа подписи по умолчанию в коде нет. Если `SESSION_SECRET` не задан, сервер придумывает случайный ключ сам. Известный всем ключ позволил бы подделать вход под любым пользователем.
- На "нет такой почты" и "неверный пароль" отвечаем одинаково и за одинаковое время.
- После 10 неудачных попыток входа на одну почту за 15 минут сервер просит подождать (ответ 429).
- Роль читаем из базы на каждом запросе, а не из cookie. Закрытые точки API проверяют вход (`require_user`) или роль администратора (`require_admin`).
- Чужой проект для пользователя не существует: на запрос к нему сервер отвечает "не найден".
- Аккаунт можно удалить (`DELETE /api/auth/me`, с подтверждением паролем). Вместе с ним удаляются проекты, версии, папки и файлы.
- Почту и пароль меняем только с текущим паролем. Неверный пароль считаем как при входе: после 10 попыток ждать 15 минут. У демо-аккаунтов профиль, почту и пароль поменять нельзя: иначе один гость запер бы остальных.
- Чужие папки и проекты сравнить, переложить или скопировать нельзя: сервер отвечает "не найден", как на любой чужой проект.
- Пароли демо-аккаунтов берем из настроек. Если их сменить, при следующем запуске они сменятся и у уже созданных аккаунтов.
- База наружу не открыта. Сервер открыт только на этом компьютере, снаружи все идет через nginx.
- nginx не называет свою версию и добавляет заголовки: браузер не угадывает тип файла, сайт нельзя встроить в чужую страницу, адрес страницы не уходит на другие сайты.
- Сервер в контейнере работает от обычного пользователя, а не от root.
- Каждая точка админки закрыта ролью администратора. Тест берет список точек из описания API, поэтому новая точка без проверки роли его уронит.
- Тип скачиваемого файла проекта определяем по расширению, а не берем из запроса загрузившего. Файл всегда скачивается, а не открывается в браузере.
- При регистрации человек отмечает согласие на обработку почты. Рядом ссылка на страницу `/privacy` "Какие данные храним и зачем".
- Кнопки демо-входа видны, только если сервер разрешает вход без пароля.
- В cookie записан отпечаток пароля. Сменили пароль: вход на этом компьютере остается, а на остальных, в том числе по украденной cookie, сбрасывается.
- Каждая закрытая точка API отвечает гостю 401, а чужой проект, папка, файл и ссылка другому пользователю не видны и не меняются. Тест обходит все точки из описания API сам: новая точка должна либо требовать вход, либо быть явно записана в список открытых.
- nginx ограничивает частоту с одного адреса: вход, регистрация и смена пароля 10 в минуту, прогон смены и отчеты 30 в минуту. Ответ 429 с понятной строкой.
- Политика CSP: странице можно грузить скрипты, стили и картинки только с нашего сайта, шрифты с Google Fonts. Даже вставленный чужой скрипт браузер не выполнит.
- В Excel текст пользователя со знаком "=" в начале записывается текстом, а не формулой: в отчете и в шаблоне для загрузки. Иначе `=HYPERLINK` из названия роли сработал бы у того, кто открыл файл. В журнале смены CSV только числа и наши слова, текста пользователя там нет.
- Открытые гостю расчеты не принимают огромный ввод: не больше 100 строк штата, 100 решений в проверке бюджета, 1500 зон плана. Иначе один запрос чувствительности или бюджета занимал сервер на минуты.
- В служебных таблицах людей не удаляют: удаление мимо нашей проверки стерло бы и общий демо-аккаунт. Аккаунт удаляет сам человек в профиле.
- Потолки на одного человека: 100 проектов, 100 папок, 1000 сохранений во всех проектах, 100 МБ файлов. Дальше сервер отвечает 422 и пишет, что удалить.
- Новый пароль при регистрации и смене не может быть из одних цифр, из списка самых частых или из трех-четырех одинаковых знаков. Старые пароли на входе не проверяем, чтобы никого не запереть.
- Ответ на неверные поля не повторяет то, что ввели, в том числе пароль.
- Файлы xlsx разбираем через defusedxml: файл с вложенными сущностями не раздует память сервера.
- Уязвимостей в библиотеках нет: проверяли pip-audit для сервера и npm audit для клиента.

## Какие данные о человеке храним

Почту, хеш пароля, дату регистрации, проекты с папками и загруженные в них файлы. Имя и компанию, только если человек сам вписал их в профиль: они не обязательны, входят по почте. Больше ничего: ни телефона, ни адреса, ни истории входов. Почта по 152-ФЗ считается персональными данными. Храним ее для одной цели: чтобы человек мог войти и вернуться к своим проектам.

## Как показываем экспертам

Есть два способа посмотреть сервис, и настройки у них разные.

Эксперт запускает сервис у себя через `docker compose up`. Настройки по умолчанию подходят: демо-аккаунты пользователя и администратора уже заведены, почта и пароль в `.env.example`, ключ подписи сервер придумает сам. Компьютер эксперта, кроме него, никто не видит.

Мы поднимаем стенд в интернете (docs/stand.md). Демо-аккаунты пользователя и администратора заводятся и там, но своих паролей, заданных через `DEMO_USER_PASSWORD` и `DEMO_ADMIN_PASSWORD`, а не паролей из `.env.example`. Вход без пароля одной кнопкой выключен настройкой `DEMO_LOGIN=false`, иначе любой посетитель вошел бы администратором. Сайт открывается только по https и только по общему логину и паролю: организатор разрешил показывать свои файлы только закрыто, а на сайте фото и каталог организатора. Экспертам даем логин и пароль стенда, почту и пароль демо-пользователя и демо-администратора в документации, которую отправляем организатору. В репозиторий эти пароли не пишем. В сценарии проверки предлагаем эксперту зарегистрироваться своей почтой. Тогда его сохранения не увидит никто другой, а в общем демо-аккаунте проекты видят все, кто в него вошел.

На экране входа отдельных кнопок для демо-аккаунтов нет: в них входят по почте и паролю, как в обычный аккаунт.

## Что пока не учли

- После выхода старая cookie еще 7 дней принимается сервером, если ее успели скопировать. Сбросить все входы можно сменой пароля, отдельного отзыва сессий нет.
- Список частых паролей короткий, около 30 штук. Полной проверки по базам утечек нет.
- Демо-администратор на стенде общий для экспертов: один может поменять каталог, другой увидит изменения. Вернуть каталог: `scripts/reset_demo`.
- Регистрация говорит, что почта уже занята. Так по ней можно проверить, есть ли у нас аккаунт с такой почтой. Так делают почти все сервисы.
- Счет неудачных попыток входа живет в памяти сервера и обнуляется при перезапуске.
- Страница документации API `/api/docs` берет оформление из интернета и без него не открывается.
- Описание API и служебные таблицы админки живут без полной CSP: их оформление берется с чужих адресов.
- Запросы, меняющие данные, защищены от подделки с чужих сайтов только настройкой cookie SameSite=lax и тем, что тела идут в JSON. Отдельного CSRF-токена нет. Поэтому стенд лучше держать на своем домене, а не на общем вроде sslip.io.
