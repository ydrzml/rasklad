# Правила данных

Как мы собираем, проверяем и храним данные для расчета. Для любой цифры можно найти откуда она взялась.

## 1. Типы источников

От более надежного к менее надежному:

| Тип | Что это | Примеры |
|---|---|---|
| Независимая проверка | испытания, сертификация, государственные реестры | протоколы испытательных лабораторий, декларации соответствия, реестр российской промышленной продукции |
| Производитель | официальный сайт, паспорт изделия, коммерческое предложение | ronavi-robotics.ru, robocv.ru |
| Эксплуатант | компания, которая использует решение | опубликованный кейс заказчика |
| Интегратор | дилер, интегратор, маркетплейс | kiit.ru, tnvst.ru, robob2b.ru |
| Организатор | материалы организатора хакатона | каталог, датасеты, примеры решений |
| СМИ | новости, обзоры, агрегаторы | отраслевые издания |

Данные организатора собраны у тех-же производителей, поэтому они не считаются независимым подтверждением. Но по ответам организатора на вопросы участников у его данных приоритет. Поэтому совпадение данных организатора и производителя дает оценку A, а значение только из файлов организатора остается слабым.

Для нормативов (начисления на ФОТ, резервы, загрузка) действует раздел 7.

## 2. Оценка достоверности

Оценка ставится каждой характеристике каждого решения и каждому значению расчетной модели в `config/model.yaml` и `config/layouts.yaml`. Для характеристик решений ее вычисляет скрипт `data/specs/rate_specs.py`, для модели ставим руками при добавлении значения. Загрузчик не примет значение без оценки.

| Оценка | Условие |
|---|---|
| S, эталон | закон, постановление, производственный календарь, ТЗ; для характеристик решений: организатор и производитель сходятся и их подтверждает эксплуатант или независимая проверка |
| A, проверено | сходятся организатор и производитель; либо производитель и эксплуатант или независимая проверка |
| B, подтверждено | сходятся два разных типа источников или больше |
| C, один источник | только производитель или только интегратор |
| D, слабо | только организатор или только СМИ |
| E, спорно | источники расходятся больше чем на 10% |
| F, нет данных | значение не опубликовано, используется допущение с обоснованием |

Уточнения:
- Значения сходятся, если отличаются не больше чем на 10%. Габариты сравниваются по каждому измерению.
- Значение из СМИ учитываеться, только если других источников нет.
- Отметка "Протестировано ФЦ БАС" подтверждает, что решение работает, но не его цифры. Так ответил организатор. Оценку она не повышает, а пишется в причине оценки как допущение.
- Значения с пометкой "устарело" (страница удалена, прежняя версия модели, старая карточка дилера) показываются, но в сравнении не участвуют.
- Значения с пометкой "аналог" взяты у похожей модели. Они тоже не участвуют в сравнении и не подтверждают цифру самого решения. Как ими пользоваться, описано в разделе "Значения по похожим моделям".
- Какое значение идет в расчет, описано в разделе 4.
- Значения, найденные автоматически и не принятые администратором, получают статус "требует проверки" и в расчет не попадают. Автоматически мы только сверяем страницы производителей (кнопка "Проверить обновления" в админке): расхождение больше 10% становится предложением, администратор принимает его с оценкой, по умолчанию C, или отклоняет, решение пишется в журнал. Подробно в журнале решений, раздел "Автообновление характеристик".
- Оценка D стоит и у данных организатора: датасет и каталог это один источник, и мы его проверяем наравне с остальными (раздел "Проверки данных организатора").
- Оценки E и F означают, что опираться на цифру нельзя. Сколько их в модели, показывает `python -m scripts.run_example`. На сегодня: S 13, A 8, B 23, C 110, D 226, E 21, F 175 из 576 значений, в модели 21 робот.
- В интерфейсе оценка показывается у каждой характеристики и влияет на уверенность рекомендации. При оценках A и B решение рекомендуется, при C и D помечается "требует проверки", при F по ключевому полю выводится "недостаточно данных".

## 3. Что хранится у значения

| Поле | Пример |
|---|---|
| значение и единица | `1500`, `кг` |
| ссылка на источник | `https://ronavi-robotics.ru/catalogue/h1500` |
| цитата | "Грузоподъемность: до 1500 кг" |
| тип источника | `производитель` |
| дата получения | нужна по ТЗ, п. 3.3.4 |
| кто проверил | участник команды |
| оценка | вычисляется |
| примечание | "у интегратора указано 1400 кг" |
| актуальность | "да" для страницы товара производителя, "устарело" для удаленной или старой страницы, "аналог" для значения похожей модели |

Где что хранится. Каталог в базе, расчетные параметры робота в конфиге. Решения, характеристики с источником, цитатой, датой и оценкой, цена изделия и задачи решения лежат в базе, их правит администратор, каждая правка пишется в журнал. Первый раз база заполняется из `data/catalog/` и `data/specs/`, затем администратор загружает выгрузку организатора файлом в админке: всего 190 позиций. Параметры, по которым считается экономика и прогон смены (скорость, батарея, зарядка, обслуживание), лежат у робота в `config/model.yaml` с источником, датой и оценкой. Цену робота расчет берет из каталога: если администратор ее поправил, в "Откуда цифры" видно, кто и когда, оценка D.

## 4. Расхождение источников

1. Характеристика получает оценку E. Все найденные значения сохраняются.
2. Если значение есть у организатора, в расчет идет оно: по ответам организатора у его данных приоритет.
3. Исключение: актуальная страница производителя дает значение хуже для окупаемости (меньше скорость или время работы, больше габариты или зарядка). Тогда в расчет идет оно, за худшую цифру отвечаем мы. Если у производителя лучше, остается значение организатора.
4. Если у организатора значения нет, в расчет идет значение, при котором окупаемость хуже.
5. Параметр включается в анализ чувствительности, чтобы было видно, меняется ли вывод.
6. Если расхождение объясняется условиями измерения, выбор записывается в примечании.

Актуальная страница производителя это карточка товара, паспорт или руководство на сайте производителя, открытые в сентябре 2026. Новости, блог, кейсы и пресс-релизы к ним не относятся. В `data/specs/sources.csv` такие строки отмечены в колонке `current` значением "да", устаревшие значением "устарело".

### Зарядные станции

Цена станции. У Ronavi своя цена, 450 000 ₽ (ronavi-robotics.ru/catalogue/charger, у дилера Stellmart 360 000). У ДиКом станция входит в комплект робота (kiit.ru: DMR 600 за 3,4 млн с НДС, "робот, автоматическая зарядная станция, RDS и лицензия"), поэтому ноль с оценкой C, а не "не учли". У остальных транспортных роботов своей цены нет, и мы берем 450 000 как цену станции до 2 кВт с оценкой C: это среднее по трем производителям, у которых цена опубликована, Ronavi 450 тыс., MiR Charge 48V 4 740 USD (shop.gibsonengineering.com; 48 В 40 А, около 1,9 кВт) и Omron LD Charging Station 5 945 USD (kingbarcode.com), по курсу ЦБ на 25.09.2026 (84,91 ₽ за доллар) это 402, 450 и 505 тыс., среднее 452. Цена станций 1-2 кВт почти не растет с мощностью, а на мощные станции автономных погрузчиков цен нет: для них 450 000 плюс 50 000 за каждый кВт сверх двух, оценка F. Мощность зарядки это емкость батареи, деленная на время зарядки; где емкости нет, считаем до 2 кВт. Уборщики уезжают на свою док-станцию, у нее цены отдельно нет или она в комплекте.

Роботов на станцию. Формула 1 + время работы / время зарядки, вниз, это верхняя граница при идеальном расписании: на живых объектах роботов на станцию в 2-5 раз меньше. Ronavi пишет 4-5 при формуле 21 (у организатора зарядка H1500 0,3 ч, это подзарядка в паузах), у Автомакона на X5 "Новая Рига" 32 станции на 67 роботов, 2 при формуле 4. Поэтому берем формулу с потолком 4, а свои числа производителей и кейсов оставляем: Ronavi 4, Автомакон 2, уборщики 1. Из формулы ниже потолка вышел только Ronavi H2000: 1 + 3 / 1,33 = 3,25, вниз 3.

### Значения по похожим моделям

Если числа нет ни у организатора, ни у производителя, ни у интегратора и в СМИ, мы берем его у похожей модели, а не придумываем. Порядок такой:

1. Организатор, производитель, интегратор и СМИ по самому решению.
2. Похожая модель того же класса: грузоподъемность, тип подъема, размер бака. В источнике пишем "аналог:" и название модели. Для характеристик решения такие строки лежат в `data/specs/sources.csv` с пометкой "аналог", общие отраслевые цифры (цены батарей, ПО, обслуживания) в `data/specs/analogs.csv`.
3. Только если нет и аналога, допущение команды с оценкой F и словами "производитель не публикует, уточняем у производителя".

Значение по аналогу получает оценку не выше D: это одна косвенная цифра, а не данные решения. Если аналогов несколько и они расходятся, берем тот, при котором окупаемость хуже, как в правиле выше.

Некоторые числа мы выводим из опубликованных, и формула записана в источнике. Средняя мощность это емкость батареи, деленная на время работы: так выходит верхняя оценка. Цена батареи это емкость, умноженная на 55 тыс. рублей за кВт*ч, худшую из найденных цен тяговых LiFePO4. Средняя скорость это 2/3 максимальной: так у Ronavi H1500, у RoboCV рядом с людьми выходит 3/4, берем худшее.

## 5. Планировка склада: норматива нет

Отдельно про `config/layouts.yaml`, где лежат шаблоны планировки и размеры стеллажей, проездов и ворот. Норматива на планировку склада не существует. СП 57.13330 прямо говорит, что размеры пролетов и шаг колонн определяются технологией, а не правилами. Все, что мы используем, это рыночная классификация складов и отраслевая практика, поэтому оценки там C и D, а не S, и писать "по нормативу" мы не имеем права.

Три места в этом файле слабее остальных, и мы их называем сами:

- ворота. Источники расходятся вдвое: одни на 500 м2 против одних на 800-1000 м2. По правилу расхождения взяли реже, одни на 1000: ворот меньше, очередь у ворот длиннее, окупаемость хуже. Оценка E;
- глубина доковой зоны и длина ряда стеллажей до поперечного проезда. Источника нет, это наши допущения, оценка F;
- пропорция здания. Длины и ширины склада нет ни в ТЗ, ни в датасете организатора, там только площадь. Пропорцию под каждую схему потока мы предположили сами, оценка F, и на шаге плана оба габарита стоят правимыми, с пометкой, что это наше предположение. Пропорция это длинная сторона к короткой, длинная лежит вдоль листа.

Еще два числа без источника появились вместе с высотами:

- верхний ярус по умолчанию ниже потолка на два метра: паллета с грузом и зазор. Оценка F, на плане правится;
- граница между подхватом паллеты с пола и штабелированием, метр подъема. Это наше правило, по нему подбор решает, кому проверять высоту яруса. Лежит в `config/model.yaml`, оценка F.

Глубина буфера у ворот выводится из доковой зоны за вычетом главного проезда, поэтому она такая же слабая, как доковая зона.

Типы стеллажей лежат там же. Для фронтального, набивного, мобильного, полочного и стеллажей, которые возит робот, мы нашли глубину ряда и проезды у производителей и в отраслевых статьях, оценки C и D. Слабые места такие:

- шаг яруса паллетного стеллажа. Прямой цифры нет ни у кого, мы оценили его из высоты груза с поддоном, зазора над грузом и высоты балки, оценка E;
- число рядов в блоке мобильного стеллажа взято с одного склада из кейса производителя, типового числа нет, оценка D;
- ширины проезда перед набивным блоком не нашли, берем проезд погрузчика: он и заезжает внутрь;
- шага полки полочного стеллажа не нашли, оценка F;
- проезда робота между стеллажами, которые он возит, не нашли, стоит наш прежний проход робозоны, оценка F.

Площадь под стеллажами план считает и показывает, но ни с чем не сравнивает: источника, с которым ее можно было бы сопоставить, у нас нет.

### Выход на режим

Помесячную кривую выхода на режим не публикует никто: ни производители (Locus, Geek+, AutoStore, Ronavi, Яндекс Роботикс), ни аналитики (McKinsey, Interact Analysis, MHI, DHL, Deloitte). Есть сроки внедрения (простые AMR 4-8 недель, товар к человеку 3-6 месяцев) и описания вроде "barely beat manual levels" в первые недели. Поэтому доли по месяцам в `config/model.yaml` наши, оценка F, с цитатами того, на что они опираются.

## 6. Проверка собранных данных

- Характеристики из открытых источников сохраняются со ссылкой и цитатой.
- У решений из демонстрационного расчета ключевые поля проверяются полностью: грузоподъемность, габариты, скорость, производительность, время работы и зарядки, минимальная ширина проезда.
- Остальные поля проверяются выборочно, каждая пятая запись. Если найдена ошибка проверяется вся группа.
- Кейсы внедрений из каталога помечаются как данные производителя и используются для сверки порядка величин, но не как входные данные расчета.

## 7. Проверка расчета

1. Эталонный пример. Для каждой формулы есть пример, посчитанный в Excel отдельно от кода. Формулу пишет один участник, эталон сверяет другой
2. Сверка с кейсами. Результат для типового объекта сравнивается с внедрениями из каталога.
3. Сверка симуляции с расчетом. Производительность из прогона смены должна отличаться от расчетной не больше чем на 5%.
4. Чувствительность. Для каждого допущения видно, насколько оно меняет окупаемость.

| Активных SKU | 2000 (1000–10000) | лист "Склад", в расчет не входит |
| Цены каталога | с НДС, без доставки, пусконаладки и интеграции; дубли считаются разными комплектациями | Дополнения, п. 6 |

Эти нормативы и остальные значения по умолчанию (взносы, рабочие часы, ставка, тарифы, параметры объекта) администратор видит и правит в админке, вкладка "Нормативы". Значение по умолчанию с источником остается в `config/model.yaml`. Правка ложится поверх, у нее свой источник, дата и оценка, которые ставит администратор, и она пишется в журнал. В "Откуда цифры" и в отчете такое значение подписано "Норматив, правил администратор" с почтой и датой правки. Какие значения открыты и почему не все, записано в `config/norms.yaml` и в журнале решений, раздел "Нормативы правит администратор, файл модели остается базой".

## 9. Проверки данных организатора

Цифры организатора мы не берем на веру, а сводим между собой. Файлы собраны из разных источников: характеристики роботов переписаны из материалов производителей, персонал взят из отраслевых бенчмарков, взносы из общей справки. Между собой их никто не сверял, и часть значений не сходится. Где расходятся, в расчете берем то, что осторожнее, и пишем об этом.

| Что проверяли | Что в файлах | Что получилось при проверке | Что делаем |
|---|---|---|---|
| Отборщики: штат против выработки | 100 отборщиков, 150 строк в час, 100 000 строк в сутки | Чтобы закрыть объем, нужно 154 ставки, а при 80 строках в час 289. Либо выработка должна быть 231 строка в час | Людей на отборе считаем от объема по нормативу, а не от штата (журнал решений, "Отбор товара: цифры датасета проверяем, люди от объема") |
| Отбор: ходьба | 150 строк в час и маршрут 25 м на строку | При скорости 0,75-1 м/с (Elbert и др., WSC 2015; arXiv 2408.01656) на дорогу уходит 25-33 секунды, а ходьба это 50-55% времени отборщика (Tompkins и др. 2003 по De Koster и др., EJOR 2007; Bartholdi, Hackman). Выходит 54-79 строк в час | Берем нижнюю границу датасета, 80 строк в час, оценка D; 150 это верхняя граница |
| H1500: производительность | "до 80–100 паллет/ч" в примерах решений | Это цикл 36–45 секунд, то есть плечо 8–12 метров. В презентации ФЦ БАС (март 2026) модельный кейс того же заказчика: пробег 200 м, 99 500 паллет в год, это 11,4 паллеты в час | Считаем производительность по циклу маршрута, паспортную цифру показываем рядом как справочную |
| H1500: зарядка | Работа 6 часов, зарядка 18 минут, то есть доступность 95% | Ronavi на своем сайте пишет "подзарядка 10–15 минут каждые 45–50 минут работы", это 80% | Берем коэффициент загрузки 75% из легенды датасета, он ближе к словам производителя |
| Взносы на ФОТ | Коэффициент 1,302, в том числе травматизм 0,2% | Для ОКВЭД 52.10 "складирование и хранение" это 5 класс риска и тариф 0,6%, то есть 1,306 | Берем 0,6% по приказу Минтруда 851н |

Так же сверяем цифры производителей между собой. Пример: сколько строк отбирают за одну подачу стеллажа, не публикует никто, но это выводится из их же данных. У Яндекс Роботикс станция дает 250 отборов в час, а робот 30-50 подач, значит на станцию нужно 5-8 роботов и на подачу приходится около одной строки. Кейс Восток-Сервиса (48 роботов на 6 станций) дает 1.04, AutoStore 13 роботов на порт. Три источника сходятся на одной строке, но это при сборке заказа по одному. В симуляции Merschformann и др. (2018, arxiv.org/pdf/1801.06703), где заказы подбирают под привезенный стеллаж, с него снимают в среднем 2,8 штуки, при 1,5 штуки на строку это 1,9 строки. Берем 1,9 с оценкой D; при 1 строке окупаемость отбора уходит за горизонт, это видно в "Что будет, если".

Сошлись: масса потоков (приемка 800 тонн в сутки, отбор 270 тонн, это 34% отгрузки), емкость склада и оборот 20 дней, штук на строку 1,5, плотность хранения, численность операторов погрузчиков против объема перевозок (18,5 паллеты в час на человека, это близко к расчетной производительности робота).
