# Расклад. Сопроводительная документация

Платформа подбора роботизированных решений и расчета экономического эффекта. Команда unicorn, хакатон "Лидеры цифровой трансформации 2026", задача №1 (ФЦ БАС).

Версия расчетной модели 0.2, документ собран по ветке `main` репозитория. Разделы 6.1-6.10 идут в порядке пункта 8.2.4 ТЗ, за ними раздел "Что мы прорабатывали сами" по пяти темам из "Дополнений для участников" и приложения. Подробности, которые в документ не поместились, лежат в `docs/` репозитория, ссылки на них даны в каждом разделе. Цифры демо-расчета в разделе 6.10 сняты с работающего сервиса на свежей базе.

## Как проверить за 10 минут

Три пути, любой из них подтверждает, что сервис считает.

1. Стенд. Адрес https://rasklad-robots.ru, вход по логину и паролю из файла доступа в материалах сдачи. Дальше войти демо-пользователем (тоже логин и пароль из того же файла) и пройти мастер со значениями по умолчанию для склада. Результат сверить с разделом 6.10, сценарий 1.
2. Локально. `git clone`, затем `docker compose up --build`, интерфейс на http://localhost:3000. Каталог организатора и наши 31 решение со всеми характеристиками загружаются в базу при первом запуске сами, вручную ничего добавлять не нужно (раздел 6.2). Если в копии репозитория файлов организатора нет (например, их убрали перед тем как открыть репозиторий), каталог поднимется только с нашими 31 решением, без позиций и фото организатора: как их дозагрузить, в разделе 6.10, сценарий 3.
3. На своих данных. На шаге 2 мастера кнопка "Скачать шаблон", заполнить его своими значениями и загрузить обратно кнопкой "Загрузить Excel или CSV": значения вне диапазона датасета не примутся, сервер объяснит, какое поле и почему (раздел 6.10, сценарий 2). Новую выгрузку каталога в формате организатора загружает администратор в админке, там же правятся нормативы (раздел 6.6, 6.7).

Стенд закрыт логином и паролем: в нем работают файлы и фото организатора, которые по его условию нельзя показывать открыто (`docs/security.md`), а в проектах пользователей могут быть чужие расчеты, которые не должны быть видны посторонним. Файлы организатора и наш дополненный каталог лежат в материалах сдачи на Диске.

## 6.1. Назначение, целевая аудитория, сценарии, границы решения

### Что делает сервис

Расклад отвечает на вопрос "окупятся ли роботы на моем объекте и какие". Человек описывает объект и работу, которую хочет отдать роботам, чертит или берет типовой план склада, выбирает решение из каталога, и сервис считает, сколько роботов нужно, во что обойдется покупка или аренда и когда вложения вернутся. Число роботов проверяет прогон смены: роботы восемь часов ездят по плану клиента, стоят в очередях и заряжаются.

### Для кого

| Кто | Что ему нужно | Где в сервисе |
|---|---|---|
| Руководитель склада или логистики | Понять, стоит ли роботизировать участок, и получить цифры для защиты бюджета | Мастер расчета из пяти шагов, отчет PDF |
| Финансист, аналитик | Проверить расчет: формулы, источники, допущения, чувствительность | Шаг экономики, "Откуда цифры", таблицы Excel, страница "Как мы считаем" |
| Интегратор, продавец решений | Быстро прикинуть парк и экономику под объект клиента | Мастер, сохранение проектов, сравнение вариантов, ссылка "поделиться" |
| Администратор платформы (ФЦ БАС) | Вести каталог решений и нормативы, следить за обновлениями | Главная администратора, каталог, нормативы, проверка обновлений |

### Основные сценарии

1. Гость без регистрации проходит пять шагов для склада и скачивает отчет PDF и таблицы Excel.
2. Пользователь сохраняет расчет в проект, возвращается к нему, делает копию "что будет, если", сравнивает проекты и версии рядом, делится версией по ссылке.
3. На одном складе считается несколько задач сразу (перевозка паллет, отбор, уборка), на задачу можно взять одно или два решения с долей объема.
4. Пользователь проверяет, влезает ли проект в бюджет, и сравнивает покупку за свои деньги, в кредит, в лизинг и аренду.
5. Администратор загружает выгрузку каталога организатора, правит характеристики и нормативы с источниками, принимает или отклоняет найденные обновления.

### Границы решения

- Склад проработан целиком: план, прогон смены, подбор и экономика.
- Аэропорт и медучреждение доходят до параметров и списка решений с объяснением. Плана, прогона смены и экономики у них нет, почему так решили, записано в `docs/decisions.md`, раздел "Аэропорт и медучреждение". Дальше у больницы план корпуса по этажам с лифтом как очередью, у аэропорта план из терминала и перрона, экран показывает это блоком "Что дальше" (раздел 6.9).
- Экономику считаем по 21 складскому роботу, у которых в модели есть расчетные параметры с источниками. Остальные позиции каталога видны в подборе с пометкой "не считается".
- Живой интеграции с WMS, ERP и 1С нет, данные объекта приходят из Excel или CSV и через API импорта.
- Результат это предварительная оценка, а не коммерческое предложение: так и написано в отчете.

Что работает целиком, частично и чего нет, подробно в `docs/mvp.md`.

## 6.2. Инструкция по развертыванию и запуску

### Запуск у себя

Нужен Docker с Compose. Интернет для работы сервиса не нужен: все данные лежат в репозитории и попадают в базу при первом запуске.

```bash
cp .env.example .env
docker compose up --build
```

Поднимаются три контейнера: `db` (PostgreSQL 16), `backend` (FastAPI на порту 8000) и `frontend` (порт 3000). При первом запуске сервер сам применяет миграции, кладет в базу каталог на 190 позиций, нормативы по умолчанию и два демо-аккаунта.

| Адрес | Что там |
|---|---|
| http://localhost:3000 | Интерфейс, лендинг |
| http://localhost:3000/calc | Расчет без входа |
| http://localhost:3000/login | Вход по почте и паролю, включая демо-аккаунты |
| http://localhost:3000/method | Как мы считаем, методика картинками |
| http://localhost:8000/api/docs | Описание API (OpenAPI) |
| http://localhost:8000/api/db | Служебные таблицы администратора |

Вернуть демо-проекты и каталог в исходный вид:

```bash
docker compose exec backend python -m scripts.reset_demo
```

### Если Docker Desktop не стартует

На части машин с Windows Docker Desktop падает с ошибкой про файл сокета. Запасной путь: Docker внутри WSL, команды в README.

### Стенд в интернете

Основной способ проверки это запуск у себя, описанный выше. Если нужен показ по ссылке, есть вторая сборка, `docker-compose.stand.yml`: она добавляет https, пароль на весь сайт и выключает демо-вход без пароля. Как ее поднять на сервере, написано в `docs/stand.md`. Наш стенд: https://rasklad-robots.ru, сайт закрыт общим логином и паролем, демо-вход без пароля выключен. Логин и пароль стенда и демо-аккаунтов на нем в материалах сдачи, в репозиторий их не кладем (`docs/security.md`).

### Разработка без Docker

Бэкенд на Python 3.12:

```bash
cd backend
pip install -e ".[dev]"
pytest
uvicorn app.main:app --reload
```

Фронтенд на Node.js 24:

```bash
cd frontend
npm install
npm run dev
```

### Проверки

На каждый pull request GitHub Actions запускает тесты и ruff бэкенда, линт, тесты, формат и сборку фронтенда, сборку образов Docker. Руками то же самое: `pytest` в `backend`, `npm run lint`, `npm test` и `npm run build` во `frontend`.

## 6.3. Архитектура, компоненты, структура данных, API

### Схема

![Схема: браузер обращается к серверу FastAPI, сервер читает и пишет в PostgreSQL и файлы](images/documentation/06-3-architecture.svg)

Клиент и сервер разделены. Все формулы живут только на сервере, в `backend/app/engine`: браузер получает готовый результат и рисует его. Так цифры на экране, в отчете PDF и в Excel всегда одни и те же.

### Стек

| Часть | Что берем | Почему |
|---|---|---|
| Бэкенд | Python 3.12, FastAPI, Pydantic 2 | Типы данных и описание API получаем сразу |
| Прогон смены | SimPy | Готовая библиотека дискретно-событийной симуляции |
| База | PostgreSQL 16, SQLAlchemy 2, Alembic | СУБД по ТЗ, работа при 50 пользователях одновременно |
| Служебные таблицы | SQLAdmin | Формы по моделям базы для администратора |
| Импорт и экспорт | openpyxl, reportlab | Excel и CSV на входе, отчет PDF и таблицы Excel на выходе |
| Вход | почта и пароль, JWT в httpOnly-cookie, argon2 | Без внешних сервисов входа |
| Фронтенд | React 19, TypeScript, Vite | Свой набор компонентов в `frontend/src/ui` |
| Редактор плана | SVG | Перетаскивание, прилипание, размерные линии |
| Проигрыватель смены | Canvas 2D | Десятки роботов и тепловая карта |

### Компоненты бэкенда

| Папка | Что делает |
|---|---|
| `app/api/` | Прием запросов и вызов сервисов, без логики |
| `app/services/` | Сценарии: собрать расчет, подбор, каталог, нормативы, проекты, бюджет, обновления каталога |
| `app/engine/economics/` | Штат, парк, сценарии, финансирование, выход на режим, показатели |
| `app/engine/plan.py` | План объекта: шаблоны, сетка, ряды, маршрут |
| `app/engine/simulation.py` | Прогон смены: лог отрезками и кривая пропускной способности |
| `app/engine/selection.py` | Правила подбора и объяснение балла |
| `app/engine/readiness.py` | Что подготовить на складе |
| `app/reports/` | Отчет PDF и таблицы Excel |
| `app/storage/` | Таблицы базы |
| `app/auth/` | Вход, роли, демо-аккаунты |
| `migrations/` | Миграции Alembic `0001`-`0008` |
| `scripts/` | Подготовка базы, возврат демо-данных, стенды проверки |

В `engine/` только расчет, без базы, файлов и веба. Содержательных чисел в коде нет: все коэффициенты берутся из `config/` вместе с источником.

### Компоненты фронтенда

| Папка | Что делает |
|---|---|
| `src/main.tsx` | Страницы по адресу, свой разбор адреса, шаг мастера в адресе |
| `src/api/` | Типы, сгенерированные из описания API (`npm run api:types`), и запросы |
| `src/app/` | Мастер: шаги, чертеж плана, смена на плане, сохранение |
| `src/features/` | Лендинг, вход, главные экраны, кабинет, админка, методика |
| `src/ui/` | Набор компонентов, токены, шрифты, роботы |

### Как идут данные

1. Пользователь вводит параметры объекта и штат.
2. `POST /api/plan/generate` строит план по шаблону, каждая правка плана уходит в `POST /api/plan/measure`. Длину маршрута и площади считает сервер.
3. `GET /api/catalog/solutions` подбирает решения под объект и план: ширину проезда, верхний ярус, пандусы.
4. `POST /api/simulation/runs` прогоняет смену и возвращает лог и кривую "сколько роботов, столько операций в час". Кривая кешируется по объекту, задаче, роботу и отпечатку плана.
5. `POST /api/calculations/preview` считает экономику по кривой, плану, штату и сценариям.
6. Интерфейс рисует готовый результат.

### Структура данных

| Данные | Где | Формат |
|---|---|---|
| Нормативы, профили объектов, задачи, расчетные параметры роботов | `config/model.yaml` | значение, источник, дата, оценка доверия |
| Шаблоны планировки, размеры стеллажей, проездов, ворот | `config/layouts.yaml` | то же |
| Поля формы с границами из датасета | `config/parameters.yaml` | путь, единица, границы, подсказка |
| Какие нормативы открыты администратору | `config/norms.yaml` | шаблон пути, раздел, границы |
| Правки нормативов | таблицы `norm_overrides`, `norm_changes` | значение, источник, дата, оценка, кто и когда |
| Каталог решений | таблицы `solutions`, `solution_specs`, `solution_uses`, `solution_photos`, `catalog_changes`, `spec_checks` | решение, характеристики с источниками, задачи объекта, журнал |
| Найденные значения характеристик | `data/specs/sources.csv`, `specs.csv` | одна строка на значение со ссылкой и цитатой |
| Пользователи и проекты | таблицы `users`, `projects`, `project_versions`, `project_files`, `folders`, `shares` | версия хранит снимок ввода, результат, версию модели и версию данных |

Каталог лежит в базе, расчетные параметры робота (скорость, батарея, зарядка, обслуживание) в `config/model.yaml`, связь по номеру решения. Цену для экономики расчет берет из каталога. Сервер держит прочитанный каталог в памяти и сбрасывает его после любой записи в таблицы каталога, поэтому правка в админке сразу видна в подборе. Правки нормативов накладываются поверх файла модели при каждом чтении.

Каждая сохраненная версия несет `model_version` и `data_version`: версия данных складывается из отпечатка файлов конфигурации, правок нормативов и состояния каталога. Рядом `data_note`, тот же отпечаток словами: версия модели и файлов, число решений и номер правки каталога, номер и дата последней правки нормативов. По ним расчет можно повторить (ТЗ, п. 3.1.5). На экране версии и на первой странице отчета человек видит только каталог и нормативы словами, без служебных номеров; сам отпечаток спрятан под "для проверки" в карточке версии и стоит в конце PDF.

Отчет PDF и Excel по сохраненной версии (из кабинета и по ссылке) собирается из сохраненного результата, расчет не повторяется: цифры такие же, как в день сохранения, а в шапке листа номер версии, дата расчета, версия модели и данных. Если нормативы или каталог с тех пор поменялись, в такой отчет не идут разделы, которые считаются заново (что будет, если, смена на плане, подготовка склада), и об этом сказано в отчете. Версию без сохраненного результата (сохранения до того, как мы стали его хранить) отчет не собирает и предлагает пересчитать. Пересчет делает новую версию с тем же вводом на текущих данных, старая не меняется.

Деньги храним в рублях и округляем только при показе. Единица видна в названии поля: `_rub`, `_months`, `_ops_per_hour`.

## 6.4. Алгоритм подбора и ранжирования решений

Подбор отвечает на три вопроса ТЗ (п. 3.4): почему решение подходит, что мешает и каких данных не хватает. Код в `backend/app/engine/selection.py`, веса в `config/model.yaml`, раздел `selection`.

### Откуда берутся кандидаты

В подбор идут решения каталога, у которых задача объекта подтверждена администратором: например, "склад, перевозка паллет между зонами". Новые позиции из выгрузки организатора получают предложенные задачи и ждут подтверждения в админке.

### Правила проверки

Каждое правило дает один из трех исходов: подходит, не подходит, неизвестно.

| Правило | С чем сравниваем | Исход |
|---|---|---|
| Процесс | Задача решения по нашей разметке, иначе сценарий из каталога организатора | другая задача: не подходит; задача размечена с пометкой "требует проверки": неизвестно |
| Грузоподъемность | Масса груза с шага параметров | меньше груза: не подходит; не опубликована или указана линейкой моделей: неизвестно |
| Ширина прохода | Проезд на плане | шире проезда: не подходит; не опубликована: неизвестно |
| Высота подъема | Верхний ярус стеллажей на плане, только для штабелеров | не достает: неизвестно, верхние ярусы остаются людям |
| Пандус | Пандусы на плане, только для мобильных роботов | уклон никто не публикует: неизвестно |
| Тип стеллажей | Набивные или мобильные стеллажи на плане | работа с торца блока: неизвестно |
| Зрелость | Статус в каталоге | эксплуатация или пилот, пилот снижает балл |

Правила высоты, пандусов и стеллажей работают, когда есть план: без него этих чисел нет. Масса груза по умолчанию 800 кг из датасета организатора.

### Три группы выдачи

- Подходит: ни одно правило не нарушено и все известно.
- Требует проверки: нарушений нет, но хотя бы одно правило вернуло "неизвестно".
- Не подходит: нарушено хотя бы одно ключевое ограничение. Такое решение не рекомендуется, но его можно "все равно посчитать" с предупреждением.

### Балл

Внутри группы решения сортируются по баллу от 0 до 1. Балл это сумма пяти слагаемых, у каждого на экране видно, сколько оно добавило и почему.

| Слагаемое | Вес | Как считаем |
|---|---|---|
| Подходит процессу | 0,30 | весь вес, если процесс подходит |
| Зрелость решения | 0,20 | весь вес при эксплуатации, половина при пилоте |
| Независимая проверка | 0,15 | весь вес при отметке "Протестировано ФЦ БАС", половина при записи в реестре 719 |
| Качество данных | 0,20 | вес * доля ключевых характеристик с оценкой A, B или C |
| Запас грузоподъемности | 0,15 | вес * min(грузоподъемность / груз, 2) / 2 |

Ключевые характеристики: грузоподъемность, минимальная ширина прохода, максимальная скорость, время работы, время зарядки, производительность. Порядок выдачи: сначала подходящие, потом требующие проверки, потом неподходящие, внутри группы по убыванию балла.

Почему так, а не машинное обучение: реальных данных о внедрениях для обучения нет, а правила и веса можно проверить руками и объяснить заказчику.

### Бюджет и второе решение

На шаге решения можно задать бюджет на старте. Сервис подбирает самый большой парк, чьи вложения со всеми статьями не больше бюджета, и прогоняет смену с этим парком, чтобы показать долю спроса, которую он вытянет (раздел 6.5, "Бюджет на старте"). На задачу можно взять два разных решения с долей объема: под кнопкой "Выбрать" у карточки стоит "Сравнить", а у выбранного решения ссылка "взять вторым к этой задаче", объем задачи тогда делится между двумя решениями.

![Шаг решения: подходящие карточками с главными цифрами, под "Выбрать" кнопка "Сравнить"](images/documentation/06-step4.png)

### Предупреждение о пике до прогона

Прогон смены идет до полуминуты, поэтому карточка заранее предупреждает, если решение может не покрыть пик задачи. Предупреждение строится только по тому, что уже есть на шаге решения: плану и парку по формуле (та же точка, что считает бюджет). Случаев три:

- отбор "товар к человеку" на плане с рядами под погрузчик: до станций отбора далеко, карточка предлагает перейти на робозону;
- по формуле нужно больше роботов, чем проверяет прогон смены (250);
- по формуле спрос не вытянуть никаким парком.

Предупреждение не запрещает выбор: точный ответ дает прогон смены. Чтобы отбор не упирался в план, типовая планировка по умолчанию зависит от задач: под "товар к человеку" робозона со станциями, иначе ряды с одной стороны. Схему, которую выбрал человек, сервис не меняет.

## 6.5. Экономическая модель

Полная методика с примерами руками в `docs/calculation.md`, картинками на странице `/method`. Код в `backend/app/engine/economics/`, значения в `config/model.yaml`.

### Из чего исходим

1. У каждой цифры есть источник и оценка доверия от S до F (раздел 6.6). Оценки E и F означают, что на цифру нельзя опираться, такие места мы называем вслух.
2. Производительность из брошюры напрямую не берем: считаем цикл по маршруту, а парк проверяем прогоном смены.
3. Сравниваем с вариантом "ничего не делать", то есть с затратами на людей, которые сейчас делают эту работу.
4. Сотрудник стоит не только оклад: взносы, травматизм, спецодежда, подбор взамен ушедших. Отпуска и болезни учитываем в числе ставок.
5. Годы целиком: вложения в год 0, затраты и эффект в конце каждого года 1..H. Горизонт 5 лет.
6. Налог на прибыль и НДС не учитываем. Цены каталога организатора с НДС.

Сценарии из ТЗ: без роботизации, покупка, роботы как услуга (аренда с выкупом).

### Единицы

Деньги в рублях с НДС в ценах года расчета, объемы в операциях (паллетах, строках, квадратных метрах уборки) в сутки и в час, время в часах, люди в ставках (полная ставка 1972 часа в год) и в людях в смене, площадь в м2, расстояния в метрах, скорость в м/с.

### 1. Сколько нужно роботов

```
часов в сутки = смен * часов в смене
пиковый спрос = объем в сутки * доля для роботов / часов в сутки * пиковый коэффициент
спрос с резервом = пиковый спрос * (1 + резерв на пик)
маршрут = средний путь по плану, без плана 0.75 * корень(площадь зоны)
производительность робота = 3600 / (2 * маршрут / средняя скорость + погрузка и выгрузка) * операций за рейс
                           (или номинал рейсов в час, если он есть для такой работы)
с учетом загрузки = производительность робота * коэффициент загрузки
парк по формуле = минимальное N, при котором N * производительность с учетом загрузки >= спрос с резервом
зарядных станций = ceil(парк / роботов на станцию)
```

Уборка считается иначе, у нее нет пикового часа: площадь смены известна с утра. Задача с признаком `steady` в конфиге считается под средний час без пикового коэффициента, с тем же резервом 15%, а прогон раскладывает участки ровно по смене. На складе датасета это один Клинботикс 400 PRO, он моет почти до конца смены.

Основной парк берется по прогону смены: роботы едут по плану, стоят в очередях у ворот и в проездах, заряжаются. Берем самый маленький парк, который вытянул спрос при трех разных seed. Формула стоит рядом проверкой. Если и 250 роботов не тянут спрос, расчет пишет, что парк не покрывает пик, и называет задачу, решение и причину. Причина в плане, если на нем нет стеллажей, до которых робот доезжает, или у отбора "товар к человеку" нет станций: тогда шаг экономики ведет обратно к плану. Иначе причина в решении, и шаг ведет к выбору другого решения.

У отбора "товар к человеку" рейс робота это подача стеллажа к станции, за подачу отборщик снимает в среднем 1,9 строки. Прогон смены засчитывает рейсу столько же строк.

### 2. Люди

```
ставок на круглосуточный пост = часов в сутки * дней в году / норма часов * (1 + потери рабочего времени)
присмотр за роботами, постов = max(минимум дежурных, парк * минут внимания на робота в час / 60), без округления вверх
операторы роботов = постов * ставок на пост
ставок до = заменяем человек * доля для роботов * рост объема (или по выработке, если она меньше)
ставок после = ставок до * выработка до / выработка на станции, если человек остается на операции, иначе 0
высвобождается = ставок до - ставок после
переучиваем = min(операторы роботов, высвобождается)
```

Полная стоимость ставки в год:

```
оклад за год = оклад в месяц * 12
взносы = min(оклад за год, предельная база) * 30% + max(оклад за год - предельная база, 0) * 15.1%
полная стоимость = оклад за год + взносы + оклад за год * травматизм + спецодежда + текучесть * подбор
```

Людей на отборе товара считаем от объема, а не долей от штата: 100 отборщиков датасета при выработке 80 строк в час не закрывают и трети его же объема, и доля от штата занижала ручную работу втрое. Почему так, в `docs/decisions.md`, раздел "Отбор товара: цифры датасета проверяем, люди от объема".

Оператором роботов становится тот же сотрудник, которого заменяем: платим как той роли плюс надбавка, по умолчанию ноль. Если операторов нужно больше, чем высвободилось, расчет пишет, скольких не хватает, но найм с рынка не закладывает: рыночной ставки оператора складских роботов мы не нашли (`docs/calculation.md`, раздел 2).

Закрытые вакансии в деньги не идут. В затраты "без роботов", в экономию, в выход на режим и в "Что будет, если" попадают только занятые ставки, то есть живые люди. Работу на вакансиях роботы делают: парк считается от объема, а закрытые вакансии видны отдельной строкой. В демо-расчете вакансий нет, его числа от этого не меняются.

### 3. Вложения на старте (CAPEX, год 0)

| Статья | Покупка | Аренда |
|---|---|---|
| Роботы | парк * цена | входят в плату |
| Зарядные станции | станций * цена | входят в плату |
| ПО управления парком | разово, один раз на производителя | входит в плату |
| Станции комплектации | станций * цена | станций * цена |
| Интеграция с WMS | по объекту | по объекту |
| Инфраструктура | по объекту | по объекту |
| Пусконаладка | парк * цена * доля | парк * цена * доля |
| Переобучение операторов | ставок * курс | ставок * курс |
| Резерв | 10% от суммы статей | 10% от суммы статей |

### 4. Затраты по годам (OPEX)

Индексы года t: зарплаты `(1 + рост зарплат)^(t-1)`, электроэнергия `(1 + рост тарифа)^(t-1)`, остальное `(1 + инфляция)^(t-1)`.

| Статья | Как считаем | Покупка | Аренда до выкупа |
|---|---|---|---|
| Люди без роботов | ставок до * стоимость * индекс | база сравнения | база сравнения |
| Люди после роботов | ставок после * стоимость * индекс | да | да |
| Электроэнергия | парк * кВт * часов работы * тариф * индекс | да | да |
| Связь | в год * индекс | да | да |
| Операторы роботов | ставок * стоимость * индекс | да | за вычетом доли поставщика |
| ТО и ремонт | парк * цена * доля * индекс | да | в плате |
| Лицензии ПО | парк * лицензия * индекс | да | в плате |
| Замена АКБ | парк * цена АКБ * индекс в год, кратный ресурсу | да | в плате |
| Плата за аренду | парк * плата в месяц * 12 | нет | да |
| Ответственность за порчу | парк * цена * доля * индекс | нет | да |

```
годовой эффект = люди без роботов - люди после роботов - OPEX роботов
денежный поток = годовой эффект - вложения в этом году (выкуп, обновление парка)
```

Аренда: плата фиксированная за робота в месяц, в конце контракта выкуп по остаточной стоимости `парк * цена * max(0, 1 - срок контракта / срок службы)`, после выкупа затраты как при покупке. Если срок службы кончается ровно к выкупу, в год выкупа парк обновляется, как при покупке. Платежи по годам, что входит в плату и как считается эффект, подробно в разделе "Что мы прорабатывали сами", пункт 4.

### 5. Показатели

```
простой срок окупаемости (ТЗ) = CAPEX / годовой эффект первого года
окупаемость по потоку = год, когда -CAPEX + сумма денежных потоков >= 0, с долей года
экономия на рубль вложений (ROI по формуле ТЗ) = сумма годовых эффектов / вложения за горизонт, пишем разами
ROI за горизонт = (сумма эффектов - вложения за горизонт) / вложения за горизонт, пишем в процентах
TCO = вложения за горизонт + сумма (люди после роботов + OPEX роботов)
амортизация = линейно, CAPEX / срок службы
NPV = -CAPEX + сумма [денежный поток / (1 + ставка)^t]
IRR = ставка, при которой NPV = 0
```

Вывод даем не по жесткому порогу, а числом, интервалом окупаемости (до 3 лет, 3-5 лет, более 5 лет, не окупается), списком рисков и текстом. Проверка для себя: `TCO без роботов - TCO сценария = сумма эффектов - вложения за горизонт`.

Если сценарий за горизонт не окупается, сервер досчитывает его на 10 лет тем же парком с заменой изношенных роботов и пишет под ответом, на каком году вернутся вложения, или что и за 10 лет не окупится. Главные цифры остаются за горизонт расчета.

### 6. Что еще учитывает модель

- Несколько задач на объекте: общее на объект (дежурные, интеграция, инфраструктура, ПО по разу на производителя, связь) считается один раз, от порядка задач итог не зависит.
- Кредит, лизинг и господдержка: способ оплаты меняет только покупку. Окупаемость в кредит считается с учетом остатка долга, показываем покрытие долга. Три меры поддержки для склада проверены по первоисточникам, недоступная мера показана с причиной. Неверные условия оплаты расчет не ломают: сервер их не берет, покупку считает за свои деньги и говорит, какое поле поправить.
- Выход на режим: первые месяцы эффект неполный, потеря ложится в затраты на людей первого года. Для перевозки и уборки первый месяц 70%, для "товар к человеку" 20% и полный эффект за 5 месяцев. Числа наши, оценка F, пользователь их правит.
- Бюджет на старте: сколько роботов влезает со всеми вложениями и какую долю спроса они вытянут за смену.
- Что будет, если: четыре главных числа сдвигаются на -20, -10, +10, +20%, по кнопке так же сдвигается каждое число расчета, список сортируется по размаху выгоды за горизонт.
- Проверка чисел робота, которые правит пользователь: срок службы робота и аккумулятора, роботов на зарядку и срок договора аренды приводятся к целым, ноль скорости или роботов на зарядку расчет не принимает. Отказ называет поле, а шаг экономики предлагает вернуть числа робота как было. Цена 0 в каталоге значит "цена не указана", расчет тогда берет цену модели.

| Данные | Файл | Как попадает в работу |
|---|---|---|

| Выгрузка каталога организатора | `data/organizer/catalog_export_v4.csv` | в базу при первом запуске той же загрузкой, что кнопка в админке; всего 190 позиций |

| Шаблоны планировки | `config/layouts.yaml` | читаются сервером |
| Поля формы с границами из датасета | `config/parameters.yaml` | читаются сервером |

Подготовку базы делает `scripts.prepare_database` при старте контейнера: применяет миграции, создает демо-аккаунты, заполняет пустой каталог. На заполненной базе повторный запуск ничего не перезаписывает.

### Оценка достоверности

У каждой характеристики и каждого значения модели есть источник, дата, цитата и оценка:

| Оценка | Условие |
|---|---|
| S, эталон | закон, постановление, производственный календарь, ТЗ |
| A, проверено | сходятся организатор и производитель, либо производитель и эксплуатант |
| B, подтверждено | сходятся два разных типа источников |
| C, один источник | только производитель или интегратор |
| D, слабо | только организатор или только СМИ |
| E, спорно | источники расходятся больше чем на 10% |
| F, нет данных | допущение команды с обоснованием |

При расхождении в расчет идет значение организатора, но если актуальная страница производителя дает худшую для окупаемости цифру, берем ее. Правила целиком в `docs/data-sources.md`.

### Данные объекта пользователя

На шаге параметров есть загрузка Excel или CSV по шаблону (`POST /api/import/template` отдает шаблон с текущими значениями). Сервер проверяет типы, единицы, обязательные поля и границы из датасета и возвращает отчет по строкам. Подставляет данные человек, сервер ничего не сохраняет сам.

### Каталог

Администратор загружает выгрузку организатора кнопкой "Загрузить выгрузку" (CSV с разделителем `;`, UTF-8). Есть режим проверки: сначала отчет, что добавится и что поменяется, потом загрузка. Ручные правки администратора повторная загрузка не затирает. Каталог выгружается в том же формате с нашими колонками ("Скачать каталог") и загружается обратно без потерь. Каждая правка пишется в журнал с тем, кто и когда.

### Нормативы

Раздел "Нормативы" в админке показывает 55 открытых значений с источником, датой и оценкой. Правка ложится поверх файла модели и сразу идет в расчет, в "Откуда цифры" и в отчете она подписана "Норматив, правил администратор". Вернуть значение из файла можно одной кнопкой. Нормативы выгружаются в Excel или CSV и загружаются тем же форматом.

### Автообновление характеристик

Кнопка "Проверить обновления" запускает в фоне обход страниц производителей из `data/specs/sources.csv`. Если цифра на странице расходится с каталогом больше чем на 10%, появляется предложение правки со ссылкой и датой. Администратор принимает его с оценкой, по умолчанию C, или отклоняет, решение пишется в журнал. Сайты, которые запрещают автоматический сбор, не открываем. Без интернета проверка идет по сохраненным страницам из `data/specs/saved`.

## 6.7. Руководство пользователя и администратора

### Пользователь: расчет за пять шагов

Кнопка "Посчитать свой склад" на лендинге открывает мастер. Пройденный шаг сворачивается в строку с итогом, шаг записан в адресе, введенное хранится в браузере и переживает перезагрузку.

Шаг 1. Объект и задачи. Четыре карточки одного вида в ряд: склад, аэропорт, медучреждение и "Другое" (весь каталог без расчета). Выбранная подсвечена рамкой и стоит на месте. Ниже отметьте работу, которую заберут роботы. На складе это перевозка паллет, отбор и уборка, можно несколько сразу, у каждой задачи виден объем в сутки и откуда цифра.

![Шаг 1: объект и задачи](images/documentation/02-step1.png)

Шаг 2. Параметры. Площадь зоны работы роботов (часть склада, где ездят роботы, в датасете "активная зона"), смены, объемы, масса груза, штат по ролям: мест в штате, сколько из них занято людьми, оклад. Значения по умолчанию уже стоят, главные в плитках с явными полями. У каждого поля единица, подсказка строкой под полем, источник и оценка под буквой. Выход за границы датасета подсвечивается рамкой поля и короткой строкой "обычно от ... до ..." на месте подсказки. Когда выбрана перевозка паллет, масса паллеты с грузом стоит среди главных полей: от нее зависит, какие роботы поднимут груз. Остальные параметры лежат в раскрывающейся строке, там же "Товар разложен по ходовости" с кнопками "Да" и "Нет" (в данных и в Excel это 1 и 0). Параметры можно загрузить из Excel или CSV кнопкой "Загрузить Excel или CSV", шаблон скачивается ссылкой рядом, файлы со старым названием поля площади загрузка тоже узнает.

![Шаг 2: главные поля и раскрытая строка остальных параметров](images/documentation/03-step2.png)

Шаг 3. План объекта. Есть три способа: типовая планировка (сквозной поток, Г-образный, "с одной стороны", робозона), свой склад по ответам на вопросы о воротах и рядах, и план по фото или скану. Любой план потом правится на чертеже на весь экран: контур здания, ряды стеллажей, ворота, проезды, перегородки, пандусы, уровни пола. Зарядки ставит программа. Типовая схема по умолчанию зависит от задач: для отбора "товар к человеку" это робозона со станциями, для остальных ряды с одной стороны. План по фото начинается с пустого здания по контуру с картинки: стеллажи и ворота человек ставит сам. Шаг можно пропустить, тогда расчет возьмет типовую схему и скажет об этом в выводе. Проверки плана идут списком под листом: если проезд между рядами уже 1,2 м, которые мы советуем, шаг предупреждает. На шаге экономики проезд уже минимума выбранного робота останавливает расчет словами, например "Между рядами 0,5 м, а Ronavi H1500 нужно не меньше 0,75 м: раздвиньте ряды", с кнопкой к плану; проезд между минимумом и 1,2 м попадает в риски.

![Шаг 3: три способа получить план](images/documentation/04-plan-ways.png)

Чертеж учит сам. При первом входе он показывает карточку трех способов, а кнопка "Как пользоваться" в любой момент предлагает два пути: "Основы" (7 шагов: режимы, движение по листу, выбор и отмена, план и объем, числа и проверки) и "Все инструменты" (по шагу на каждую кнопку). После основ идет практика: человек сам ставит ряд, ворота и буфер у ворот и смотрит проверки плана. В основах и в практике есть кнопка "Назад". Шаг засчитывается, когда вещь появилась на листе. Если практика шла на готовом плане, после "Готово" план возвращается таким, каким был. Карточку практики можно свернуть в плашку в углу листа, а когда человек тянет по листу, она сворачивается сама. "Начать заново" после подтверждения сразу стирает начерченное и строит чистый план тем же способом.

Шаг 4. Решение. Подходящие решения стоят карточками, "требуют проверки" и "не подходят" свернуты. На карточке цена, аренда и строками главные цифры из каталога: скорость, производительность, грузоподъемность, с единицами источника; нет цифры, нет строки. Выдачу можно отсортировать по производительности: это порядок, а не сравнение, единицы у решений разные. Ссылка "почему это решение здесь" раскрывает, почему подходит, что мешает, откуда цифры, а в группе "требуют проверки" написано, что именно не проверили. Если решение может не покрыть пик задачи, карточка предупреждает об этом до прогона смены (раздел 6.4). Под кнопкой "Выбрать" стоит "Сравнить". У выбранного решения ссылка "взять вторым к этой задаче": объем задачи поделится между двумя решениями. Можно задать бюджет на старте. Кнопка "Начать подсчет" запускает расчет, полоса прогресса показывает этапы.

Шаг 5. Экономика. Сверху ответ словами, он же заголовок экрана: "Покупка окупится за 1,1 года", под ним "За 5 лет дешевле, чем без роботов, на 149,1 млн ₽" и четыре числа со ссылками "как посчитано". Сводка всегда открывается покупкой, аренда переключателем рядом. Под ответом строка "Чем платить: Свои деньги / Кредит / Лизинг" и кнопка "Условия и господдержка". Кредит или лизинг открывают панель условий справа: ползунки суммы, ставки и срока (до 7 лет), четыре числа (свои деньги на старте, платеж в месяц, переплата, окупаемость), меры господдержки под выбранный способ и платежи по годам. Ниже оговорка, что это оценка. Сразу под ответом смена на плане, открытая: роботы едут по вашему складу, переключатель "Роботы", "План смены" и "Как прошла смена" меняет то, что нарисовано на плане, строка под ним говорит, что сейчас на плане, справа парк со строкой "9 роботов вытягивают спрос 149 в час, 8 уже не хватает", итоги смены и узкое место. Дальше блоки списком строк: у каждой заголовок, главные числа и кнопка "Подробнее", полный блок раскрывается прямо под строкой, можно открыть несколько. Строки: "Три сценария за 5 лет" (плитки, график накопленных затрат, риски, все показатели ТЗ: окупаемость, ROI, NPV, IRR, деньги по годам), "Куда уходят деньги" (статьи на старте, в год и за 5 лет, выход на режим), "По задачам", если задач несколько, "Что будет, если", "Что подготовить на складе" и "Откуда цифры" (как подобран парк с кривой парка, что мы приняли за вас, источники всех цифр). В блоке "Что мы приняли за вас" можно поправить цену, обслуживание и срок службы робота. Ссылки "как посчитано" сами раскрывают нужный блок. Расчет не пропадает: после входа он сразу сохраняется в новый проект.

Если парк не покрывает пик, вместо экономики стоит сообщение с задачей, решением и причиной. Когда причина в плане (нет стеллажей, до которых робот доезжает, или нет станций отбора), кнопка "Вернуться к плану" ведет на шаг 3. Когда в решении, кнопка "Поменять решение" ведет на шаг 4. Если в блоке "Что мы приняли за вас" введено невозможное число робота, отказ называет поле, а кнопка "Вернуть числа робота как было" возвращает значения.

### Пользователь: чертеж DXF под планом

На шаге "План объекта", в карточке "По фото плана", есть кнопка "Загрузить чертеж DXF". Чертеж из AutoCAD сохраняют как DXF ("Файл", "Сохранить как", тип файла DXF) и загружают; файл можно и бросить в рамку. Сервер находит единицы и габарит и отдает линии по слоям. В окне видна картинка и слои с галочками: размеры, штамп и надписи выключены сразу, стены и стеллажи включены. Единицы берутся из файла; если их в файле нет, программа угадывает их по размеру здания и просит проверить, а выпадающий список позволяет выбрать свои. Кнопка "Положить под план" строит здание по слою со стенами и кладет чертеж под лист в точном масштабе, юго-западный угол чертежа в юго-западный угол здания. Дальше стены, ворота и ряды обводят по подложке, как по фото. Кнопка "Слои и единицы" в правой колонке открывает то же окно снова, пока шаг открыт.

Кнопка "Построить план" делает из чертежа сам план. Для этого в окне у каждого слоя выбирают, что на нем: стены, стеллажи, ворота или "не использовать". Начальный выбор программа угадывает по имени слоя (wall, стен, rack, стелл, door, ворот и похожие), слои с размерами и надписями остаются без роли. Слой должен быть отмечен галочкой и иметь роль, иначе в план он не идет. Нужен хотя бы один слой со стенами. Сервер строит здание по самому большому замкнутому контуру на слоях стен, ряды стеллажей по замкнутым фигурам и блокам на слоях стеллажей, ворота по значкам у стены и буфер за воротами. Пустое здание того же размера строится как при ответах "без стеллажей", затем в него ложатся ряды, ворота и буфер; зарядку ставит программа, как обычно. В колонке справа сказано, что нашли и что пришлось приблизить или пропустить. Дальше план правят руками как любой другой.

Как читаются чертежи (ограничения, о них же сказано в окне):
- Все края встают на сетку в метр, как на плане: ряд в 1,1 м становится рядом в 1 м, двойная рама в 2,2 м рядом в 2 м.
- Секции стеллажей вплотную и одной толщины склеиваются в один ряд; ряды с проездом между ними остаются отдельными.
- Чертеж, повернутый целиком (стены стоят под одним углом), разворачивается по стенам. Подложка в этом случае не кладется, потому что картинка осталась бы повернутой.
- Стеллаж, стоящий под другим углом, заменяется прямоугольником той же площади вдоль ближайшей оси, о чем есть предупреждение. Фигура не прямоугольной формы (буква Г) берется рамкой.
- Стены под углом к осям остаются в контуре, но ложатся по клеткам ступеньками, о чем есть предупреждение. Двойные линии стен: берется самый большой контур, толщина не учитывается. Незамкнутые линии стен собираются в контур по общим концам; не сложились, берется рамка вокруг линий.
- Ворота: значок (отрезок, дуга, блок) не дальше полутора метров от стены здания; ворота ставятся на ближайшую сторону рамки здания, а не вдоль косой стены. Простенок между воротами не меньше метра. Буфер ставится на всю ширину ворот одной стены и до первого стеллажа; нет места, буфера нет, и это сказано.
- Стеллажи вне контура здания, фигуры размером с половину здания (это контур, а не стеллаж) и слишком мелкие фигуры пропускаются со счетчиком. Больше 4000 рядов не берем.
- Не читаются штриховки и заливки, надписи, вложенные чертежи глубже шести уровней и объекты вне модели.

Что принимаем: текстовый DXF до 8 МБ. DWG и двоичный DXF отклоняются с подсказкой, как пересохранить. Что рисуем: отрезки, полилинии, дуги, окружности, эллипсы, сплайны и содержимое блоков и размеров; надписи, штриховка и заливки не рисуются. Линии далеко от основного чертежа (потерянные объекты) убираются, об этом сказано в окне. Типы стеллажей, высоту ярусов, направления рядов и поперечные проезды из чертежа не берем: ряд получает толщину из чертежа и проезд по соседним рядам, остальное человек ставит на плане.

Защита: файл чужой, поэтому разбирается отдельным процессом со сроком 25 секунд и лимитом памяти (на Linux), не больше двух разборов одновременно (остальным "сервер занят"), не больше 400 тысяч объектов и 3 миллионов точек, ответ не больше 6 МБ. Ничего из файла не исполняется и не сохраняется на сервере, картинка живет в браузере. В nginx обе точки (`/api/plan/dxf` и `/api/plan/dxf/build`) стоят в зоне heavy, как генерация плана. Роли слоев с экрана проверяются на сервере: не больше 500 слоев, роль только walls, racks или doors, единица от 0,0001 до 1000 метров. Код: `backend/app/services/dxf_underlay.py`, `dxf_worker.py`, `dxf_plan.py` (геометрия плана), `frontend/src/app/plan/dxf.ts`, `DxfDialog.tsx`.

## 6.9. Известные ограничения и план развития

### Ограничения модели и данных

- Штучный отбор "товар к человеку" всегда считается по компактной робозоне (часть склада по ползунку "Под отбор роботами"), какой бы план ни начертил человек: на рядах под погрузчик до станций в разы дальше, и парк не сходится. Остальные задачи считаются по его плану. Если план не робозона, на шаге 5 у отбора одна строка: "Отбор посчитан по компактной робозоне, как ставят такие системы".
- Если у решения, выбранного на отбор, в config нет цены станции отбора, экономику этой задачи не считаем и пишем: "У этого робота нет данных станции отбора: выберите систему товар к человеку (Ronavi M)". Молча взять станции за ноль значило бы занизить вложения.
- В демо-расчете склада 26 значений из 75 имеют оценку E или F. Сильнее всего влияют: внимание оператора на робота, строк за одну подачу стеллажа, цена аренды (у H1500 цифра 2019 года), интеграция, инфраструктура, пусконаладка, ТО, лицензии, цена АКБ, тариф на электроэнергию.
- Прогон смены скорее оптимистичен: на реальном складе Восток-Сервиса роботов вдвое больше нашей формулы. В прогоне нет пополнения стеллажей в робозоне, приемка и отгрузка не разделены, встречные роботы в двустороннем проезде тормозят как попутные.
- Модель отбора товара сверена с внедрениями только частично. Цифры датасета проверены и поправлены (80 и 250 строк в час, 1,9 строки за подачу), но 1,9 остается оценкой D: на цифрах S&S Activewear наша модель дает 184 робота против их 600 (340 на первой очереди), то есть роботов для большого склада мы занижаем. Станции при этом сходятся: 53 против 50. Системы AS-RS P и AS-RS B стоят в подборе с пометкой "требует проверки", но в экономику не идут: расчетных параметров для них нет.
- Не учтены налог на прибыль и НДС, остаточная стоимость роботов в конце горизонта, помесячный поток и поэтапное внедрение, выходные пособия при сокращении, экономия на ошибках и травмах, выгода через выручку при росте пропускной способности.
- Аренда только с фиксированной платой, без оплаты за операцию и смешанной схемы.
- В подборе нет правил ровности пола, температуры, лифтов и наличия WMS: этих полей нет в каталоге.
- У позиций организатора вне наших 31 складского решения характеристик нет, в экономику они не идут.
- Список задач объекта пока в коде, справочник ролей с окладами в файле `config/roles.yaml`: администратор правит их не в админке.
- Загрузка параметров из Excel и CSV только для склада, у аэропорта и медучреждения ручной ввод.
- Открытой страницы каталога для гостя нет: решения он видит на шаге 4.
- Проверка обновлений каталога запускается кнопкой, по расписанию не идет.
- Нагрузку в 50 одновременных пользователей (ТЗ, п. 4.3.1) мы не замеряли.

- Смешанный парк на одной задаче считается по группам: у каждого решения своя кривая производительности, взаимные помехи групп на общих проездах в одной смене не моделируются. При нескольких группах на общих проездах производительность может быть завышена.
- Нулевой парк: если принудительно задать 0 роботов, модель в отдельных случаях оставляет затраты на внедрение или показывает высвобождение людей. Эти случаи зафиксированы тестами как известные ошибки.

### Что в работе

- Аэропорт и медучреждение полным путем (план, прогон смены, экономика): работа идет в отдельной ветке, готово около половины; в эту версию не вошло, потому что расчет нужно оценить и сверить с реальными внедрениями.
- Чертеж склада: улучшаем по отзывам тестировщиков.
- Исследование пользователей: материалы опросов и интервью войдут в следующую версию материалов сдачи.

### План развития

| Что | Зачем | Как сделаем |
|---|---|---|
| Английский язык интерфейса и отчета | Иностранные заказчики и производители | Тексты вынести в словари, переключатель уже стоит в настройках с меткой "скоро"; отчет PDF и Excel по тем же словарям |
| Аэропорт и медучреждение с планом и экономикой | Сейчас путь заканчивается списком решений | Медучреждение: доставка по этажам (лекарства и расходники из аптеки в отделения) и уборка коридоров. План корпуса по этажам: этаж это такой же план, как у склада, только выше по высоте, между этажами переключатель. Этажи связывает лифт, в прогоне смены он очередь, как зарядка: в кабину входит несколько роботов, лифт может быть общим с людьми. Эффект считаем как высвобожденные часы персонала по цене часа, а не сокращение ставок. Аэропорт: перевозка багажа по перрону и уборка терминала. План из двух частей, терминал и перрон (открытая площадка, большие расстояния, мороз), маршрут тягача от сортировки к стоянке самолета и обратно. Спрос идет волнами по рейсам: кривую по часам строим из суток и пикового часа датасета, это допущение с оценкой F. Экономика по тем же формулам, что у склада |

### Сценарий 2. Свой склад через шаблон

Проверяет загрузку параметров объекта из Excel или CSV и проверку границ (раздел 6.6, "Данные объекта пользователя").

1. Открыть http://localhost:3000/calc, выбрать склад и задачу, "Дальше: параметры".
2. На шаге 2 нажать "Скачать шаблон": файл приходит с текущими значениями по умолчанию (`GET /api/import/template`).
3. Поправить в шаблоне нужные поля своими значениями объекта. Если поставить число вне диапазона датасета, например отрицательную площадь или оклад в тысячи раз больше обычного, сервер это не примет.
4. Кнопкой "Загрузить Excel или CSV" загрузить файл обратно. Сервер проверяет типы, единицы, обязательные поля и границы из датасета и возвращает отчет по строкам: что принято, что отклонено и почему. Значения вне диапазона в расчет не попадают, а строка объясняет, какое поле и какая граница нарушена.
5. Пройти оставшиеся шаги мастера с загруженными значениями, посчитать и сверить, что параметры в отчете совпадают с файлом.

### Сценарий 3. Обновить каталог администратором

Проверяет загрузку выгрузки организатора через админку (раздел 6.6, "Каталог") — тот же путь, которым каталог пополняется, если файлов организатора нет в самой копии репозитория (например, их убрали перед тем как открыть репозиторий).

1. Войти демо-администратором: почта и пароль в `.env.example` (`DEMO_ADMIN_EMAIL`, `DEMO_ADMIN_PASSWORD`) или, на стенде, в документации для экспертов.
2. Открыть "Каталог" (`/admin`). Если файла организатора не было, в списке только наши 31 решение.
3. Нажать "Загрузить выгрузку" и выбрать файл `catalog_export_v4.csv` (CSV с разделителем `;`, UTF-8, формат организатора: колонки id, Название, тип, статус, компания, описание и так далее, раздел 6.6). Сначала показывается отчет, что добавится и что изменится, без записи в базу, затем загрузка подтверждается.
4. После загрузки в каталоге должны появиться позиции организатора (всего 190 при полной выгрузке), с пометкой источника "организатор" у полей. Фото у этих позиций не появится: они прикладываются отдельно, отдельного массового способа их загрузить в админке нет, только по одной картинке на карточке решения.
5. Повторная загрузка того же файла ничего не ломает: строки без изменений отмечаются как есть, ручные правки администратора не затираются.

Дальше в том же разделе "Нормативы" (`/admin?tab=norms`) можно поправить значения с источником и датой: кнопка "Загрузить файл" принимает CSV или Excel в том же формате, что отдает "Скачать нормативы".

## Что мы прорабатывали сами

В "Дополнениях для участников" (раздел 7) организатор перечислил пять тем, которые команда прорабатывает сама. Ниже по каждой: что решили, правила, цифры и где это лежит в коде и конфигурации. Чего в модели нет, так и написано.

### 1. Условия исключения неподходящих решений

Что решили. Решение не рекомендуется, если нарушено ключевое ограничение объекта. Если нужной характеристики нет ни в одном источнике, решение не выбрасываем, а ставим в группу "требует проверки" и пишем, чего не хватает. Выдача делится на три группы: подходит, требует проверки, не подходит (раздел 6.4). Неподходящее решение можно "все равно посчитать", экран предупреждает об этом.

Правила для склада (`backend/app/engine/selection.py`, пороги в `config/model.yaml`, раздел `engine.selection`):

| Что проверяем | Откуда берем | Не подходит | Требует проверки |
|---|---|---|---|
| Задача решения | Разметка задач `data/catalog/uses.csv`, в базе после подтверждения администратором | решение для другой задачи или задача не размечена | задача размечена с пометкой "требует проверки": решение может ее делать, но это никто не проверял |
| Грузоподъемность | Масса груза на шаге параметров, по умолчанию 800 кг из датасета | поднимает меньше груза | не опубликована; в каталоге линейка моделей; у отбора стационарная система, которая подает свою тару, а не стеллаж |
| Ширина прохода | Проезд на плане клиента | роботу нужно шире | не опубликована |
| Высота подъема | Верхний ярус стеллажей на плане, только у штабелеров (подъем выше 1 м) | | не достает до верхнего яруса |
| Пандус | Пандусы на плане, только у мобильных роботов | | уклон не публикует ни один производитель |
| Тип стеллажей | Набивные и мобильные стеллажи на плане | | робот работает только с торца блока |
| Зрелость | Статус в каталоге | | пилот не исключает, а снижает балл |

Бюджет на старте решение не исключает: сервис показывает, сколько роботов влезает в него со всеми вложениями и какую долю спроса они вытянут за смену.

Отбор товара. Кроме Ronavi M, который возит стеллажи к станции, восемь решений каталога могут подойти, но это никто не проверял: шесть низких роботов с подъемом (Ronavi H1500, AMR 800, AMR 1500, DMR 600, DMR 1200, Семабот) и две системы, которые организатор называет "товар к человеку" (AS-RS P и AS-RS B). Они стоят в "требует проверки" с причиной на карточке, а не в "не подходит". Две системы AS-RS в экономику не идут: расчетных параметров робота для них нет, карточка так и пишет. Остальные 22 решения склада для этой задачи не подходят по делу: уборка, инвентаризация, сортировка, погрузчики и штабелеры, хранение.

Предупреждение о пике решение не исключает: карточка до прогона смены говорит, что решение может не покрыть пик, если отбор "товар к человеку" стоит на плане под погрузчик или по формуле нужно больше 250 роботов (раздел 6.4).

Для аэропорта и медучреждения свои проверки (`data/facilities/solutions.csv` и `backend/app/services/facility_catalog.py`): можно ли купить (прототип и снятая модель не подходят), работа на морозе -25 °C для перрона, ширина коридора больницы, этажи и лифт, масса тележки или контейнера. Если диапазон температуры не опубликован, это "не проверили", а не "подходит".

Проверки плана дополняют подбор со стороны объекта: хватает ли проездов, доезжает ли робот до мест у стеллажей, не перекрывают ли зарядки и станции комплектации проезд. Станция между рядами стеллажей или на месте, откуда берут груз, не проходит проверку.

Чего нет: ровности пола, температуры склада, лифтов на складе и наличия WMS. Этих полей нет в каталоге организатора и мы их не нашли у производителей, правила ждут данных (раздел 6.9).

Решения: разделы "План идет в подбор решений", "Отметка "Протестировано ФЦ БАС" подтверждает работоспособность, а не цифры", "Шаг решения: карточками только подходящие, остальные списком строк", "Аэропорт и медучреждение: путь до списка решений, без плана и экономики" в `docs/decisions.md`.

### 3. Допущения по отсутствующим или неполным данным

Что решили. Цифру без источника не прячем и не придумываем молча. Порядок такой: организатор, производитель, интегратор, СМИ; если нет, значение похожей модели с пометкой "аналог" и оценкой не выше D; если нет и аналога, допущение команды с оценкой F и словами "производитель не публикует, уточняем". При споре источников берем цифру организатора, но если актуальная страница производителя дает худшую для окупаемости, берем ее (`docs/data-sources.md`, разделы 2 и 4).

Сколько таких значений. Во всей модели 594 значения: S 13, A 9, B 28, C 117, D 222, E 25, F 180. В демо-расчете участвуют 86 значений, из них 32 с оценкой E или F. Счетчики по всей модели выдает `python -m scripts.run_example`, список значений расчета на экране в блоке "Откуда цифры", в отчете на последней странице.

Как показываем влияние на результат:

- В ответе расчета список слабых значений, на шаге экономики их число и каждое с источником и оценкой.
- Вывод содержит риски словами. В демо-расчете три: план типовой, а не клиента; выход на режим (экономия первого года меньше на 0,93 млн ₽); кто ставит груз на верхний ярус, если робот возит только по полу.
- "Что будет, если" сдвигает каждое число расчета на -20, -10, +10 и +20% и сортирует по размаху выгоды за горизонт. На складе с паллетами сильнее всего двигают результат длина смены (127 млн ₽ за 5 лет), доля работы водителя, которую забирает робот, и люди в штате (по 85), оклад водителя (79), объем и скорость робота (по 20), роботов в строю (19); цена робота 14, интеграция около 1,6.
- Главные допущения правятся руками: цена, обслуживание и срок службы робота в блоке "Что мы приняли за вас", выход на режим и условия оплаты на шаге экономики, нормативы у администратора.

Цифры датасета мы проверяем источниками и логикой, а не берем на слово. Пример отбора товара: базовая выработка отборщика в датасете 150 строк в час, но в том же листе маршрут 25 м на строку. При обычной скорости отборщика 0,75-1 м/с и ходьбе в половину рабочего времени (Tompkins и др. 2003 по De Koster и др. 2007) выходит 54-79 строк в час. Поэтому берем нижнюю границу датасета, 80. Еще штат отборщиков датасета (100 человек) не закрывает и трети его же объема, поэтому людей на отборе считаем от объема по нормативу, а не долей от штата. Вместе с выработкой станции 250 строк в час (Яндекс Роботикс, факт Kiva 200-250) это меняет вывод по отбору: было "не окупается ни при каком объеме", стало 2,07 года при покупке на готовом разборе (2,59 по формуле). Проверку на внедрениях S&S Activewear, Decathlon и Яндекс Лавки мы записали в `docs/calculation.md`, раздел "Проверка на реальных внедрениях".

Решения: разделы "Отбор товара: цифры датасета проверяем, люди от объема", "При расхождении берем цифру организаторов, паспортное "до" справочное", "Доверие к цифре оцениваем одной шкалой, включая нормативы расчета", "Выход на режим включен по умолчанию, два вида задач" в `docs/decisions.md`, список недостающих данных в `docs/calculation.md`, раздел "Каких данных не хватает".

### 4. Логика экономической модели "роботы как услуга"

Что решили. Услугу считаем как фиксированную плату за робота в месяц с выкупом в конце контракта. Эту схему публикуют производители (Ronavi, Яндекс Роботикс), и ее можно проверить руками. Оплату за операцию и смешанную схему пока не считаем (раздел 6.9). Код: `build_years`, `buyout_share`, `raas_setup_amortization` в `backend/app/engine/economics/scenarios.py`, условия у каждого робота в `config/model.yaml`, раздел `raas`.

Структура платежей:

| Платеж | Когда | Как считаем | Демо-расчет |
|---|---|---|---|
| Разовый платеж за внедрение | год 0 | интеграция, инфраструктура, пусконаладка, переобучение, подбор, резерв 10% | 11,49 млн ₽ |
| Плата за услугу | каждый год контракта | парк * плата в месяц * 12, на срок контракта не меняется | 9 * 100 000 * 12 = 10,8 млн ₽ в год |
| Ответственность за порчу | каждый год контракта | 1% цены роботов в год с инфляцией | 0,24 млн ₽ в первый год |
| Продление | после контракта | плата индексируется на инфляцию за срок контракта | 12,15 млн ₽ в год с 4 года |
| Выкуп, отдельный кейс | конец контракта | парк * цена * (1 - срок контракта / срок службы), дальше затраты как при покупке | 9 * 2,7 * (1 - 3/5) = 9,72 млн ₽ в конце 3 года, окупится за 1,08 года |

Что входит в плату: роботы, зарядки, ПО, ТО, ремонт и замена АКБ. Энергия, связь и операторы остаются на клиенте. Часть присмотра за парком поставщик может взять на себя (параметр `support_share`), по умолчанию ноль: сколько именно, никто не публикует.

Распределение во времени. Контракт 36 месяцев, расчет идет по годам, поэтому срок контракта кратен году. Если клиент продлевает, а не выкупает, плата индексируется на инфляцию за прошедший срок: `плата * (1 + инфляция)^(срок * номер продления)`. На экране всегда выкуп, продление доступно через API (`raas_buyout: false`). Разовый платеж за внедрение списывается линейно за срок контракта, выкуп за оставшийся срок службы.

Оценка эффекта. Эффект года это затраты на людей без роботов минус люди после роботов и все затраты услуги. Показатели те же, что у покупки: окупаемость по накопленному потоку, ROI, TCO, NPV, IRR. Базово аренда без выкупа, как найм: каждый год сравниваем плату, сервис и присмотр с людьми. В демо-расчете поток аренды по годам 29,58, 33,61, 36,73, 38,71, 42,28 млн ₽: аренда выгоднее людей с первого года, внедрение 11,5 млн ₽ возвращается за 0,39 года. TCO 87,43 млн ₽ против 76,91 у покупки, NPV 110,00 млн ₽ против 107,63: аренда дороже за 5 лет на 10,5 млн ₽, но на старте требует 11,5 млн ₽ вместо 41,4 и дает больший NPV, потому что платежи растянуты на все годы. Выкуп в конце договора показан отдельным кейсом (`scenarios[].buyout`): с ним за 5 лет 79,11 млн ₽. Сводка на экране открывается покупкой, услуга переключателем рядом, какой сценарий дешевле за горизонт, помечено на плитке. Если у решения нет цены услуги, сценарий не показывается; у объекта из нескольких задач услуга есть, только если цена есть у решений всех задач.

Откуда цена. Цена услуги с источником есть у 8 роботов из 21: Ronavi H1500 (100 000 ₽ в месяц, 2019 год, оценка D), Ronavi M, два уборщика Клинботикс, MARK 2 SE, РУБИ-С-03, Автомакон АК-SC80 и Unit. У остальных 13 аренду производитель не публикует, и мы берем ее как у H1500 в доле от цены робота, оценка F. Проверка на кейсе Восток-Сервиса: при цене 100 тыс. ₽ окупаемость за 6 месяцев сходится, если внедрение стоило до 28 млн ₽ (`docs/calculation.md`, "Проверка на реальных внедрениях").

Решения: разделы "Аренда роботов: фиксированная плата с выкупом", "Сценарии сравнения взяты из ТЗ", "Сводка экономики всегда открывается покупкой" в `docs/decisions.md`, раздел 5 в `docs/calculation.md`.

| Аэропорт | 12 | 6 | 6 | характеристики, проверки по параметрам объекта, без экономики |
| Медучреждение | 18 | 10 | 8 | то же |

Критерии отбора для склада (`data/specs/README.md`): сценарий "Внутрискладская логистика", "Сортировка грузов", "Инвентаризация склада" или "Уборка помещений" (36 позиций), минус 4 в статусе "разработка" (их нельзя купить) и Pick by Voice (программа без оборудования). Для аэропорта и больницы из каталога подходят 6 и 3 позиции, этого мало, чтобы показать выбор. Добавили решения под задачи из датасета организатора (уборка терминала, буксировка тележек, консультации пассажиров, доставка по этажам с лифтом, перевозка тележек с питанием и бельем, обеззараживание), и только если у решения есть страница производителя или дилера с характеристиками. Уборщики из каталога подходят и больнице, их отметили для обоих объектов. У каждого решения в `data/facilities/solutions.csv` записано, почему взяли, какие ограничения и можно ли купить его в России.

Источники. В `data/specs/sources.csv` около 1 600 значений по 51 решению, каждое со ссылкой, цитатой, датой и типом источника: производитель 579, организатор 390, интегратор 187, СМИ 128, эксплуатант 12, остальные без источника с пометкой. Больше всего значений с сайтов Ronavi, kiit.ru, robob2b.ru, Waybot, Автомакона, RoboCV, R2B, ДиКом, Pudu, Gausium, Aethon. Оценки: A 36, B 28, C 183, D 65, E 22, F 113 из 447 характеристик. Отраслевые цифры и похожие модели (батареи, ПО, обслуживание) в `data/specs/analogs.csv`.

Как каталог обновляется. Администратор загружает новую выгрузку организатора, ручные правки она не затирает. Кнопка "Проверить обновления" сверяет характеристики со страницами производителей, расхождение больше 10% становится предложением, администратор принимает или отклоняет его (раздел 6.6). Сайты, которые запрещают автоматический сбор, не открываем.

Чего нет: характеристик у 132 позиций каталога без объекта (другие отрасли) и автоматического поиска новых решений. Новые позиции добавляет администратор.

Решения: разделы "Для склада берем 31 решение из каталога", "Решения для аэропорта и медучреждения: каталог плюс открытые источники", "Автообновление характеристик: сверяем страницы производителей, правку принимает администратор", "Характеристики собираем полуавтоматически, принимает человек" в `docs/decisions.md`.
