# Архитектура

Как устроена платформа, кто за что отвечает и как мы пишем код. Требования ТЗ, из которых это выросло, собраны в [requirements.md](requirements.md).

## Ограничения

- На экспертизе проект запускают без нас, поэтому он должен подниматся одной командой `docker compose up`.
- Код, тесты и их читаемость оценивают в технической проработке.
- Каждую формулу экономики сверяем с примером, посчитанным вручную.

## Стек

| Часть | Что берем | Почему |
|---|---|---|
| Бэкенд | Python 3.12, FastAPI, Pydantic 2 | Типы данных и описание API (OpenAPI) получаем сразу |
| Симуляция смены | SimPy | Готовая библиотека для симуляции событий, свою писать ненужно |
| База данных | PostgreSQL 16, SQLAlchemy 2, Alembic | ТЗ требует СУБД и работу при 50 пользователях одновременно |
| Админ-панель | SQLAdmin | Роль администратора обязательна, формы редактирования строятся сами по моделям базы |
| Импорт и экспорт | openpyxl, reportlab | Загрузка Excel и CSV, отчет в PDF, таблицы в Excel |
| Вход | email и пароль, JWT в httpOnly-cookie, argon2 | Без подтверждения почты и входа через сторонние сервисы |
| Фронтенд | React 19, TypeScript, Vite | |
| Переходы между шагами | свой разбор адреса | Страниц немного, шаг хранится в адресе, поэтому работает кнопка "назад" |
| Запросы и состояние мастера | fetch и localStorage | Старый запрос отменяется, когда двигают ползунок; введенное не пропадает после перезагрузки |
| Графики | свой SVG | Внешний вид графиков настраиваем полностью сами, подписи в точках экрана |
| Анимации | CSS и View Transitions API | Одна кривая движения на весь интерфейс, при уменьшении движения отключаются |
| Компоненты | свой набор в `frontend/src/ui` | Внешний вид свой, доступность с клавиатуры проверяем сами (docs/design.md) |
| Редактор плана | SVG | Перетаскивание, прилипание и размерные линии получаются сами |
| Проигрыватель смены | Canvas 2D | Тридцать роботов и тепловая карта, SVG этого не вытянет |

## Структура данных

В базе пользователи, проекты с версиями и каталог, нормативы и расчетные параметры роботов лежат в `config/` с источниками. Правки администратора ложатся поверх файлов в базе.

| Данные | Где | Формат |
|---|---|---|
| Нормативы расчета, профили объектов, операции, роботы | `config/model.yaml` | значение с источником, датой и оценкой доверия |
| Шаблоны планировки склада и размеры стеллажей, проездов, ворот | `config/layouts.yaml` | то же, четыре схемы потока |
| Поля формы с границами из датасета | `config/parameters.yaml` | путь к значению, единица, границы, подсказка |
| Какие нормативы открыты администратору | `config/norms.yaml` | шаблон пути, раздел, жесткие границы, что меняет в расчете |
| Правки нормативов администратором | база, таблицы `norm_overrides` и `norm_changes` | значение, источник, дата, оценка, кто и когда; журнал было и стало |
| Каталог решений | база, таблицы `solutions`, `solution_specs`, `solution_uses`, `solution_photos`, `catalog_changes`, `spec_checks` | правит администратор в /admin; при первом запуске база заполняется из `data/catalog/` и `data/specs/`, каталог организатора администратор загружает файлом в админке |
| Найденные значения характеристик | `data/specs/sources.csv` и `specs.csv` | одна строка на значение со ссылкой и цитатой |
| Пользователи и проекты | база, таблицы `users`, `projects`, `project_versions`, `project_files`, `folders`, `shares` | версия хранит снимок введенного, результат, версию модели и версию данных |

Таблицы создают миграции Alembic `0001`-`0008`, при запуске их применяет `scripts.prepare_database`.

Каталог в базе, расчетные параметры робота в конфиге. Подбор, счет решений на первом шаге и раздел решений в отчете читают каталог из базы: решения с подтвержденной задачей объекта, их характеристики, оценки и цену. Сервер держит прочитанный каталог в памяти и сбрасывает его после любой записи в таблицы каталога, поэтому правка в админке видна в подборе сразу. Скорость, батарея и обслуживание лежат у робота в `config/model.yaml` с источниками, связь с каталогом по номеру решения (`catalog_id`). Цену для экономики расчет берет из каталога (`backend/app/services/catalog_prices.py`), если она там есть. Каталог выгружается в формате организатора с нашими колонками (`GET /api/admin/catalog/export`) и загружается обратно через `/import`. Решение без робота в модели в подборе видно, но помечено "не считается". Код: `backend/app/services/selection.py`.

Нормативы: файл модели остается значением по умолчанию, правка администратора лежит в базе и накладывается поверх при каждом чтении модели (`overlay` в `backend/app/engine/model_config.py`, сервис `backend/app/services/norms.py`). Перед чтением сервер сверяет номер последней записи журнала нормативов: поменялся, значит правки перечитываются и сбрасывается кеш поиска парка. Версия данных расчета учитывает правки нормативов.

При первом запуске `scripts.prepare_database` кладет в базу наш каталог из `data/catalog` и `data/specs`. Выгрузку организатора администратор загружает файлом в админке (раздел "Каталог решений", кнопка "Загрузить выгрузку"): вместе с нашим каталогом получается 190 позиций. В админке каталог виден списком или деревом (`GET /api/admin/catalog/tree`). Версия данных сохраненного расчета учитывает каталог в базе: число решений и последнюю запись журнала правок.

Автообновление характеристик: `backend/app/services/catalog_updates.py`, API `/api/admin/updates`. Сервер в фоне обходит страницы производителей из `data/specs/sources.csv`, результат лежит в таблице `spec_checks`, расхождение ждет решения администратора. Без интернета проверка идет по строкам из `data/specs/saved`.

Правила: деньги в рублях, единица видна в названии поля, у каждого значения справочников есть источник и оценка доверия, расчет хранит версию модели и версию данных, чтобы его можно было повторить (ТЗ, п. 3.1.5).

## Как идут данные

1. В мастере пользователь вводит параметры объекта и штат.
2. `POST /api/plan/generate` строит план объекта по шаблону планировки, дальше человек его правит, и каждая правка уходит в `POST /api/plan/measure` с задержкой 150 мс. Ответ несет числа и план: зарядку ставит программа, и ее место могло измениться. Длину маршрута и площади считает сервер, браузер только рисует.
3. Пользователь выбирает решение. `GET /api/catalog/solutions` получает с плана ширину проезда, верхний ярус и число пандусов и подбирает под них.
4. `POST /api/simulation/runs` прогоняет смену по плану и возвращает лог отрезками и кривую "сколько роботов, столько операций в час". Кривая кешируется по объекту, операции, роботу и отпечатку плана.
5. `POST /api/calculations/preview` считает экономику по этой кривой, плану, штату и сценариям. Когда двигают ползунок, запрос уходит с задержкой 150 мс, а предыдущий отменяется.
6. Интерфейс только рисует готовый результат.

Все формулы лежат в одном месте, в `backend/app/engine`. В TypeScript формулы не копируем: две копии со временем разойдутся, и цифры на экране перестанут совпадать с отчетом.

## Как пишем код

Бэкенд:
- В `engine/` только расчеты: без обращений к базе, файлам и FastAPI.
- В `api/` нет логики, только прием запроса и вызов сервиса.
- В коде расчета нет содержательных чисел, все коэффициенты берутся из `config/` вместе с источником.
- Если меняем формулу, обновляем [calculation.md](calculation.md) и пересчитываем эталон вручную.
- Проверки: ruff, позже добавим mypy.

Фронтенд:
- TypeScript в строгом режиме, без `any`.
- Разделы в `features/` не импортируют друг друга, общее выносим в `ui/`, `charts/` и `api/`.
- Графики получают готовые данные и ничего не считают.
- Цвета, шрифты и отступы берем только из `styles/`.
- Проверки: eslint и prettier.

Общее:
- На каждую задачу отдельная ветка и pull request, в `main` напрямую не пушим. Кто то один из команды смотрит изменения.
- Коммиты пишем в повелительном наклонении: "Добавить расчет запуска".
- GitHub Actions на каждый pull request запускает тесты, проверки кода и сборку фронтенда.
- Пароли и ключи только в `.env`, в репозитории лежит `.env.example`.

## Интерфейс

По ТЗ пользователь должен пройти основной сценарий без инструкции (п. 4.5.2).

- Между шагами переходим плавно, короткими анимациями 150–350 мс.
- Когда двигают ползунок, цифры меняются плавно, а не скачком.
- Вместо спиннеров робот-персонаж показывает, что происходит: загрузка, идет расчет, готово, ошибка.
- Шаг хранится в адресе, введенные данные в localStorage, кнопка "назад" возвращает на прошлый шаг с данными.
- Пока данные грузятся на месте блоков видны заготовки.
- В ошибке пишем, что случилось и что сделать.
- Если в системе включено уменьшение движения, анимации отключаются.
- Интерфейс работает от 1366 на 768 (требование ТЗ) и нормально выглядит на телефоне.
- Все элементы доступны с клавиатуры.

| API | pytest, `backend/tests/api` | ответы, доступ по ролям у каждой точки, импорт, каталог туда и обратно, ошибки |
| Миграции и образ | pytest | миграции строят те же таблицы, что модели; Dockerfile копирует все, что читает сервер |
| Фронтенд | `node --test` | геометрия плана, числа, окупаемость, IRR, повтор смены |

Проверки на GitHub на каждый PR: тесты и ruff бэкенда, линт, тесты, формат и сборка фронтенда, сборка образов Docker.

## Запуск

```bash
cp .env.example .env
docker compose up
```

Интерфейс откроется на http://localhost:3000, описание API на http://localhost:8000/api/docs. При первом запуске создаются демо-пользователь и демо-администратор (почты и пароли в README и `.env`), каталог на 190 позиций и нормативы по умолчанию.
